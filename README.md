# КОНТУР

Локальный помощник инженера для осмотра промышленного оборудования. Задача хакатона «Кибер 102» от КСТ ЭНЕРГО ИНЖИНИРИНГ (постановка — `manuals-021` среди материалов организатора).

Приложение объединяет цифровую карточку оборудования, телеметрию, видимые признаки дефектов, объяснимые правила и журнал осмотров. Работает на локальном сервере без выхода в интернет. Решение по оборудованию принимает инженер: отсутствие предупреждений не подтверждает исправность.

## Состояние

| Готово | Впереди |
|---|---|
| Основной агрегат Wilo CronoLine-IL 65/160: ряды организатора как телеметрия, моточасы в работе, правила по уставкам | Дообученный детектор: нужны размеченные снимки |
| Сверка правил с колонкой «Диагноз»: 482 из 500 и 500 из 500, ни одного пропущенного отклонения | Проверка на человеке вне команды |
| Живой осмотр с камеры: рамки, подтверждение по кадрам, запись в журнал с кадром | Презентация и репетиции защиты |
| Опознание по QR и по заводской табличке, без сети | OPC UA (сейчас только Modbus) |
| Вход по почте и паролю, роли, отчёты Excel и PDF | |
| Сервер ввода/вывода: эмулятор Modbus TCP и адаптер в API | |
| Паспортный агрегат AMS PCP, двигатель и редуктор: 15 правил по документам; демо Н-101: 12 правил | |
| Печатный стенд A4 и доступ с телефона по HTTPS в локальной сети | |

Полный план и приоритеты — в [docs/plan_to_do.md](docs/plan_to_do.md). Требования заказчика — в [docs/organizer-answers.md](docs/organizer-answers.md): при расхождении с планом правы они.

## Быстрый старт

Нужны Python 3.10 или новее (проект рассчитан на 3.11), Node.js 24 и npm 11. Docker не нужен. Команды выполняются из корня проекта; при первой установке зависимости скачиваются из сети.

### macOS и Linux

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
npm ci
./scripts/dev/start.sh
```

### Windows

```powershell
python -m venv .venv
& ".\.venv\Scripts\python.exe" -m pip install -r requirements.txt
npm ci
& ".\scripts\dev\start.ps1"
```

Скрипт собирает фронтенд, если сборки ещё нет, и запускает сервер в текущем терминале; остановка — `Ctrl+C`. Затем откройте:

- [приложение](http://127.0.0.1:8000);
- [документацию API](http://127.0.0.1:8000/docs);
- [стенд для печати](http://127.0.0.1:8000/stand.html) — лист A4: схема с маркером Hiro для AR-меток, QR-код и учебный шильдик латиницей для опознания. Схема и QR пересобираются командой `node scripts/qa/export-stand.mjs`;
- [презентацию](http://127.0.0.1:8000/presentation.html) — 16 слайдов, стрелки для переключения, печать в PDF по слайду на страницу.

### Режим разработки

В первом терминале — API без сборки фронтенда:

```bash
./scripts/dev/start.sh --dev
```

На Windows — `& ".\scripts\dev\start.ps1" -Dev`. Во втором терминале:

```bash
npm run dev
```

Интерфейс откроется на [127.0.0.1:5173](http://127.0.0.1:5173); Vite перенаправляет запросы `/api` на порт 8000. После изменений фронтенда пересоберите его (`npm run build`), чтобы их увидел сервер на 8000.

База осмотров создаётся в `data/inspection.db`. Путь меняется переменной `APP_DB_PATH`.

## Вход и роли

Вход по почте и паролю включён по умолчанию. При первом запуске с пустой базой приложение предлагает создать администратора; дальше учётные записи добавляет только он (профиль → «Учётные записи»). Пароли хранятся хешем scrypt, сессия — в cookie HttpOnly на 12 часов, пять неверных попыток подряд блокируют вход на минуту.

| Роль | Что доступно |
|---|---|
| Инженер | Осмотр, камера, записи «Проверка» и «Замечание», карточки, журнал |
| Мастер | Всё инженера, «Обслуживание» и «Замена», ряды измерений, материалы, отчёты |
| Администратор | Всё мастера и учётные записи |

Автор записи в журнале — тот, кто вошёл; подставить чужое имя через запрос нельзя. Для тестов и браузерных сценариев вход отключается переменной `KONTUR_AUTH=off`, тогда все действия выполняются от имени «Демо-инженера».

## Локальная модель

Qwen3-VL 4B через llama.cpp работает на том же сервере и отвечает на `POST /api/vision`; экран осмотра её больше не вызывает — он работает с живым видео, детектор признаков подключается отдельно. Облачных вызовов нет: клиент принимает только адрес на самом сервере (`127.0.0.1`).

Подготовка модели скриптом сейчас рассчитана только на **Windows с видеокартой NVIDIA**: скрипт скачивает сборку llama.cpp для CUDA и файлы модели в `.runtime/` и `.models/`.

```powershell
& ".\.venv\Scripts\python.exe" scripts\data\prepare-local-model.py
& ".\scripts\dev\start-local-model.ps1"
```

Без видеокарты добавьте `-Cpu`. Модель слушает `http://127.0.0.1:8081`; адрес и имя модели задаются в `.env` (образец — `.env.example`).

На macOS и Linux приложение работает без модели: карточки, правила, история, ряды и библиотека доступны, а живой осмотр передаёт кадры на сервер и прямо сообщает, что детектор признаков ещё не подключён. Порядок запуска модели на этих системах ещё не описан.

Проверить, отвечает ли модель:

```bash
.venv/bin/python scripts/qa/check-vision.py
```

Это проверка связи, а не точности распознавания.

## Сервер ввода/вывода (эмулятор Modbus)

На объекте текущие значения приходят с сервера ввода/вывода по OPC UA или Modbus; для прототипа заказчику достаточно эмулятора. Эмулятор проигрывает ряды основного агрегата по Modbus TCP, одна часовая запись в 2 секунды:

```bash
.venv/bin/python scripts/dev/io-emulator.py --port 5020
```

```bash
KONTUR_IO=modbus://127.0.0.1:5020 ./scripts/dev/start.sh
```

Тогда «текущее значение» основного агрегата сервер берёт из регистров, а не из файла; карта регистров — в `services/api/app/io_server.py`. Без `KONTUR_IO` приложение показывает последнюю запись ряда. Сверку правил с колонкой «Диагноз» пересобирает `scripts/qa/series-agreement.py` в `docs/reports/series-vs-diagnosis.md`.

## Детектор признаков

Живой осмотр работает и без детектора: кадры доходят до сервера, а экран прямо говорит, что детектор не подключён. Чтобы подключить детектор без обучения (OWL-ViT или OWLv2, Apache 2.0), нужны дополнительные библиотеки и веса — около 0,6 ГБ на модель. Скачиваются один раз, пока есть интернет; сервер сам ничего не скачивает.

```bash
.venv/bin/pip install -r requirements-detector.txt
```

```bash
.venv/bin/python scripts/data/prepare-detector.py owlvit
```

```bash
KONTUR_DETECTOR=owlvit ./scripts/dev/start.sh
```

Скорость на своём компьютере — `.venv/bin/python scripts/qa/bench-detector.py owlvit`. Это замер скорости, а не точности: без обучения качество распознавания для показа непригодно, подробности — в [архитектуре](docs/architecture.md), раздел «Живой осмотр».

### Дообученный детектор RF-DETR

Основной путь — RF-DETR (Apache 2.0 для размеров Nano, Small и Medium), дообученный на наших классах. Источники и их лицензии описаны в [scripts/train/sources.json](scripts/train/sources.json): каждая выгрузка Roboflow в формате COCO кладётся в `.models/rfdetr/sources/<id>/`. Собственные снимки команды — источник `own`; только они попадают в проверочную часть выборки.

```bash
.venv/bin/pip install -r requirements-train.txt
```

```bash
.venv/bin/python scripts/train/prepare-dataset.py
```

```bash
.venv/bin/python scripts/train/train-rfdetr.py --size small --epochs 40
```

```bash
.venv/bin/python scripts/train/evaluate-detector.py rfdetr
```

```bash
KONTUR_DETECTOR=rfdetr ./scripts/dev/start.sh
```

Оценка печатает полноту и точность по каждому классу на собственных снимках и сохраняет выбранный порог рядом с моделью; сервер берёт его оттуда. Обучение на MacBook идёт медленно, тот же скрипт без изменений работает на машине с видеокартой NVIDIA.

## Проверки

Тесты Python, Ruff и сборка фронтенда:

```bash
./scripts/dev/check.sh
```

На Windows — `& ".\scripts\dev\check.ps1"`.

Браузерные сценарии Playwright ждут, что API работает на порту 8000, а Vite — на 5173. Для них удобнее отдельная база, чтобы тесты не писали в рабочую:

```bash
KONTUR_AUTH=off APP_DB_PATH="$TMPDIR/kontur-e2e.db" ./scripts/dev/start.sh --dev
```

```bash
npm run dev
```

В третьем терминале, браузер ставится один раз:

```bash
npx playwright install chromium
```

```bash
./scripts/dev/check.sh --browser
```

Python запускайте без флага `-I`: в изолированном режиме не видны пакеты, установленные для пользователя, и часть тестов молча пропускается.

Проверки подтверждают поведение кода: правила, обработку неполных данных, раздельную историю, выдачу файлов. Они не доказывают точность распознавания дефектов и работу камеры на телефоне.

|---|---|
| `apps/web/` | Интерфейс: React, TypeScript, Vite; презентация, стенд и AR в `public/` |

## Данные

- **Материалы организатора** лежат в `data/reference/organizer/` вместе с манифестом. Репозиторий приватный, пока не подтверждено право их публиковать. Новые файлы добавляются через манифест с контрольной суммой.
- **Паспортные объекты** (AMS PCP, двигатель, редуктор) собраны из переданных документов. Чего в документах нет, остаётся неизвестным; например, ни в одном паспорте не заполнена дата ввода в эксплуатацию, поэтому остаточный ресурс не рассчитывается.
- **Демонстрационный насос Н-101** и его 14 сценариев синтетические. Его нормативы и телеметрия выдуманы и ни к одному документу не относятся.
- **Ряды организатора** не принадлежат паспортному агрегату: в них 2923–2986 об/мин против 260 у насоса AMS PCP. Заказчик разрешил прикрепить их к центробежному агрегату решением команды.
- **Изображения** со стоковыми водяными знаками и сгенерированные изображения непригодны для обучения и публикации; классификация каждого файла — в `data/registry/sources.json`.

Приложение не управляет оборудованием, не прогнозирует время до отказа и не диагностирует внутренние дефекты по изображению. Нормативный срок службы не является прогнозом отказа.
