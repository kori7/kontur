# Покрытие и границы MVP

Матрица описывает контракт прототипа и границы проверки. Зафиксированные интеграционные результаты приведены ниже, актуальный прогон запускается командами из README. Отдельный синтетический сценарий для каждого правила проверяет воспроизводимость логики, а не промышленную точность.

## Правила

| ID | Гипотеза / предмет проверки | Основные входы | Визуальный источник в MVP |
|---|---|---|---|
| R01 | Смазка или механический износ подшипника | Рост вибрации и температуры, ток в базовом диапазоне | Не требуется |
| R02 | Признаки кавитации | Рост вибрации и падение входного давления | Не требуется |
| R03 | Возможная расцентровка | Осевая вибрация, температура, слегка повышенный ток | Не требуется |
| R04 | Возможный износ проточной части | Расход, перепад давления, мощность, базовый КПД, сопоставимый режим | Не требуется |
| R05 | Регламентное обслуживание | Наработка, выполненное обслуживание, интервалы | Не требуется |
| R06 | Утечка с перегревом | Жидкость у уплотнения, рост вибрации и температуры | Демоданные / ручной ввод / адаптер модели |
| R07 | Возможная проблема крепления | Отсутствующий крепёж или коррозия, низкочастотная вибрация, 1x | Демоданные / ручной ввод. Модель только для крепежа |
| R08 | Возможная проблема масла | Низкий уровень или изменение вида масла, устойчивое превышение температуры | Демоданные / ручной ввод |
| R09 | Возможная проблема электрического контакта | Видимое повреждение и дисбаланс фазных токов либо локально измеренная температура | Демоданные / ручной ввод |
| R10 | Несогласованные показания давления | Аналоговое и электронное показания одного участка, время, единицы | Демонстрационное значение аналогового прибора |
| R11 | Отсутствие кожуха | Визуальное наблюдение независимо от телеметрии | Демоданные / ручной ввод / адаптер модели |
| R12 | Усиленные признаки кавитации | Падение давления, рост высокочастотной вибрации, дополнительный признак потока/аудио | Демоданные, расширенный ручной контракт API |

Всего 14 сценариев: `normal`, `r01`–`r12`, `missing_data`. Сценарий может затрагивать несколько правил. R02 и R12 объединяются в одно предупреждение по общей гипотезе с сохранением идентификаторов и оснований.

Все пороги демонстрационные. `clear` значит, что конкретное правило не сработало на доступных входах. `insufficient` значит, что выводу не хватает сведений. `not_applicable` значит, что правило к этому типу оборудования не применяется, и тогда оно сопровождается причиной. Ни одно из этих состояний не подтверждает исправность оборудования.

Все двенадцать правил написаны для синтетического центробежного агрегата и действуют только для типа `centrifugal_pump_unit`. Для документированного одновинтового эксцентрикового агрегата, двигателей, редукторов, арматуры и трубопроводов все двенадцать возвращают `not_applicable`: своих правил у этих типов пока нет. Область действия задана в `services/api/app/diagnostics/applicability.py`.

## Проверяемое поведение

| Область | Автоматическая проверка | Что остаётся за пределами проверки |
|---|---|---|
| Правила | Положительный пример каждого правила, исключение необходимого условия, пропуски, давность, одна точка, границы формул, объединение гипотез | Соответствие реальному насосу и нормативам изготовителя |
| API | Загрузка конфигурации, сценарии, сохранение, валидация запросов | Производственная нагрузка и доступность |
| Хранилище | Сохранение снимков анализа и изображений с дедупликацией, связь события с анализом, история после нового экземпляра хранилища, раздельная история по `equipment_id`, миграция базы без этой колонки | Защита от правки файла администратором, резервное копирование |
| Каталог объектов | Полнота каталога относительно реестра, карточка документированного объекта, неизвестная дата ввода, нормативы только у быстроизнашиваемых узлов, отказ проиграть демосценарий на другом объекте, отказ привязать событие к осмотру другого объекта, статус `not_applicable` с причиной | Соответствие карточки реальному агрегату на площадке |
| Ряды измерений | Отсутствие идентификатора оборудования в окне, сохранение часового шага и исходной строки Excel, оценка только измеряемых каналов, сравнение с уставками описания, отказ по границам окна, раздельность g и мм/с | Принадлежность рядов какому-либо агрегату (опровергнута инвентаризацией) |
| Библиотека материалов | Совпадение итогов с инвентаризацией, видимость происхождения и пригодности каждого файла, побайтовое совпадение выданного файла с оригиналом, адресация только по идентификатору манифеста, отказ на попытку обхода пути | Права на публикацию стоковых файлов |
| Визуальный адаптер | Структура, классы, `bbox`, качество `good`/`limited` без выдуманного `confidence`, ошибки и тайм-ауты | Живой доступ к модели и качество на реальных дефектах |
| Интерфейс | Сценарий осмотра, история, адаптивная вёрстка, неизвестные измерения, накопление ручных наблюдений, ресурс узла после замены | Физическая камера, реальные условия освещения |
| QR / AR | 10 меток компонентов, обнаружение Hiro и скрытие меток после потери на видеопотоке печатного стенда | Сканирование и устойчивость трекинга на целевом телефоне |

Команды: `scripts/check.ps1` для Python/Ruff/сборки, `scripts/check.ps1 -Browser` для дополнительной браузерной проверки при запущенных API и Vite. Количество тестов намеренно не зафиксировано в презентации: оно меняется с набором проверок и не измеряет качество диагностики.

Интеграционная проверка от 13.11.2026: четыре E2E-сценария прошли. Отдельная проверка AR на поданном видеопотоке печатного стенда вернула `markerDetected=true`, `markerHiddenAfterLoss=true`, `errors=[]`. Физический телефон в этом прогоне не участвовал. Число Python-тестов здесь не закрепляется, поскольку набор ещё расширяется.

## Статус важных ограничений

- **Живая модель:** проверка `GET /v1/models` вернула HTTP 401 и `unauthorized client detected`. Шлюз ограничивает API-клиент. Новый ключ успешно прочитан из пользовательского окружения Windows без пробельных символов. Это не доказывает его невалидность, повторная смена ключа не подтверждена как решение. Нужен разрешённый API-доступ для клиента. Успешное распознавание не заявляется.
- **Данные:** вся телеметрия, паспорт, временные интервалы и нормы синтетические. Реальный размеченный набор пока отсутствует.
- **Визуальный объём:** адаптер принимает три класса. Ручной интерфейс дополнительно поддерживает низкий уровень масла и повреждение контакта. Автоматическое считывание манометра, аудиоанализ и внутренние дефекты не реализованы.
- **AR:** трекинг Hiro на печатном стенде с 10 метками компонентов. Обнаружение и потеря маркера проверены на видеопотоке стенда. Автоматического определения положения деталей реального насоса нет. Физический телефон ещё не проверен, для его камеры нужен доверенный HTTPS-адрес.
- **Ресурс:** замена пересчитывает наработку и нормативный остаток выбранного узла от сохранённой наработки замены. Другие узлы не обнуляются. Неизвестная наработка остаётся неизвестной. Нормативный срок и срок до ТО не являются прогнозом времени до отказа.
- **Снимки осмотра:** полученное сервером изображение сохраняется в таблице `images` с дедупликацией. Анализ содержит `image_id`, история показывает его через `/api/images/{image_id}`. `AnalyzeRequest.image` необязателен и позволяет сохранить снимок при ручном осмотре.
- **Эксплуатация:** локальный демонстрационный сервис без пользовательской авторизации и промышленного аудита. История добавляется без редактирования через приложение, но файл SQLite не защищён от администратора.

## Условия следующего этапа

1. Согласовать нормы и рекомендации по документации изготовителя и правилам площадки.
2. Получить синхронизированную телеметрию и независимую разметку реальных изображений.
3. Подтвердить внешний API, измерить ложные тревоги и пропуски отдельно по каждому визуальному классу.
4. Испытать QR, камеру, видимость меток и потерю маркера на целевых телефонах.
5. Подготовить авторизацию, права доступа, политику хранения изображений, аудит и резервное копирование для пилота.
